# 微信小游戏框架目标架构与实施路线

路线更新于 2026-11-23。核心、业务和案例拆分、构建目标与颜色匹配已实现。当前命令和新增场景步骤见[架构与使用指南](ARCHITECTURE_AND_USAGE.md)，验证结果见[QA 文档](QA.md)。

## 1. 基线与目标

保留已经验证的技术组合。应用用 TypeScript 编写，微信小游戏由 `game.js` 加载 ES2019 产物。用 `three-platformize@1.133.3`、WebGL1 与 OrbitControls 渲染 3D，用 `pixi.js@8.23.0` 绘制 UI。初始目标是让不同小游戏复用同一个运行时、场景切换和资源装载方式。

- **渲染**保持一个微信上屏 Canvas、一个 WebGL 上下文和一个帧循环。先 Three 后 Pixi，渲染器交接时重置状态，Pixi 保留 Three 的画面。
- **输入**保留微信原生触摸桥。HUD 根据起点捕获手势并接收释放或取消，其他手势继续交给 OrbitControls。
- **模型**保留适配版 GLTFLoader、静态纯 JS Draco、内嵌贴图、Toon 渐变和动画回归。约 4.13 MB 的 Littlest Tokyo 通过微信下载和版本缓存。
- **兼容性**保留 Pixi 延迟初始化、`navigator`、`globalThis.performance` 和 `globalThis.Intl` 映射、WebGL1 的 `LuminanceFormat` 与 DPR 上限 2。
- **验证边界**开发者已确认旧基线的模型和 HUD 操作。本轮以及各阶段的 GPU、设备输入、普通扫码和微信工具分包结果分别验收。Text、图片纹理和滚动组件保持专项验收。

## 2. 模块划分

### 2.1 重构前后的边界

| 重构前 | 当前实现 |
| --- | --- |
| 入口和业务共同读取多个编译布尔值。 | `main.ts` 读取 `BUILD_PROFILE` 并选择目标，业务只接收可选模型工厂。 |
| `PixiHud.ts` 同时创建渲染器、适配微信 Canvas，并默认创建操作诊断面板。 | 框架提供渲染与手势接口，基础与模型案例显式装配诊断面板。 |
| `loadModelGLB.ts` 查 `modelCatalog.ts`，通用装载链路依赖 Littlest Tokyo 的资源配置。 | 场景提供 URL、缓存键和版本，加载器负责下载、校验、解码、缓存与取消。 |
| 配装台的 3D、配色数据和 HUD 分散，`AppHud.ts` 负责首页、配装台、模型加载以及重试显示。 | 按场景就近放 3D、UI 和私有数据，应用层负责导航及跨场景装配。 |

### 2.2 推荐目录

下列目录已落地。当前命令与实际源码路径见[架构与使用指南](ARCHITECTURE_AND_USAGE.md#2-运行架构)。

```text
game.js                         微信宿主入口，加载 dist/game.bundle.js
src/
  main.ts                       唯一 TypeScript 构建入口，选择启动目标
  framework/
    runtime/                    Canvas、场景切换、RAF、窗口和前后台
    platform/                   微信全局适配、触摸与坐标转换
    ui/                         Pixi 渲染、环境初始化、HUD 与手势接口
    assets/                     包内加载，以及可选的 GLB／Draco 加载
  game/
    startGameApp.ts             业务启动、首页入口、返回及重试协调
    scenes/
      home/                     首页场景与导航 UI
      workbench/                三维场景、配色 UI 与配色数据
      littlest-tokyo/           模型场景、资源描述与专用显示
      color-match/              限时玩法、3D 场景与 Pixi UI
    ui/                         共用小图集及工具栏布局
  examples/
    basic/                      立方体与操作面板回归
    model/                      GLB／Draco 独立回归
    pixi-ui/                    包内图集、数字及点按诊断
    webgl2/                     原生探针，分别装配基础和模型场景
media/                          运行时实际读取的包内素材
```

`framework` 接收场景工厂和 HUD 工厂。`game` 负责把业务场景接到框架上。独立案例可复用首页立方体或模型场景工厂，直接装配所需的 HUD。图集坐标和数字样式跟随实际使用它们的 UI，通用图片解码放在框架。每个场景目录保留相机、控制器、UI 和私有资源的所有权，退出时由场景释放。单文件案例可保持单文件。

参考 Phaser 官方 TypeScript 模板把启动文件、游戏组装和场景目录分开，以及 Three.js 用独立案例和清单组织示例。这里采用同样容易定位的目录和命令索引，继续使用本项目的微信宿主、Three 与 Pixi 适配。[Phaser 官方模板](https://github.com/phaserjs/template-vite-ts#template-project-structure) · [Three.js 案例索引源码](https://github.com/mrdoob/three.js/blob/dev/examples/index.html)

### 2.3 构建入口和新增场景

七个 `npm` 命令保持现有含义。编译选择集中在一个 `BUILD_PROFILE` 字符串，覆盖 `basic`、`model`、`app`、`app-model`、`webgl2`、`webgl2-model`、`pixi-ui`。`src/main.ts` 使用可被 esbuild 常量折叠的显式分支和模块路径，启动模块组装场景、HUD 和日志。业务入口接收可选的模型场景工厂，同一包内通过 `switchScene` 切换场景。

新增业务场景时，参考配装台，在 `game/scenes/` 下放置该场景的工厂、视图和所需资源描述，在业务启动模块添加入口。工厂接收运行时提供的 Three 场景等对象，返回相机、更新和释放行为。共享输入、渲染和前后台逻辑由框架处理。新增独立诊断时，在 `examples/` 添加案例及启动函数，只有需要单独出包的案例增加构建目标。用现有命令索引记录如何构建、需要什么资源、应该看到什么及关键日志。

## 3. 场景切换与失败恢复

1. 启动创建一次 Canvas、渲染器和 RAF。首页、几何回归场景和模型场景在同一个运行时中切换。断网时首页和基础 HUD 仍可用。
2. 切换过程中保留全局 HUD 与返回操作。旧场景结束前取消手势和异步工作，释放其控制器监听、动画、几何、材质及私有纹理。新场景独立设置相机和渲染配置，避免上一个模型场景的 ACES 等状态泄漏。
3. 模型场景传入资源描述，获得下载及解析状态。失败要结算为可显示的错误，支持重试或返回。快速往返时，上一尝试的回调只能清理其资源，不能改写当前场景。
4. 处理已复现的 Draco 拒绝与 `GLTFLoader.parse` 等待悬挂。验收覆盖坏 GLB 头、坏 Draco 数据、非 200 和断网。只有内容可用后才将该版本视为有效缓存，现有失败缓存需有失效方案。
5. 切后台时暂停调度并清理手势临时状态。恢复时继续当前场景，首帧不累计后台时间。场景切换生命周期与微信前后台分别建模。

## 4. 构建和资源发布

| 发布层 | 内容与原则 |
| --- | --- |
| 主包 | 微信启动文件、首屏必需的代码、基础 HUD 和小体积本地素材。小图可用单独文件随包发布，并计入包体。 |
| 普通分包 | 后续关卡代码、可选功能和它们专用的小资源。在 `game.json` 声明，使用 `wx.loadSubpackage` 加载。普通分包使用主包共享能力，避免重复构建 Three、Pixi 和平台单例。 |
| HTTPS 静态服务或 CDN | 大模型、高清纹理、音频等内容。按内容版本指定 URL，经合法下载域名和 `wx.downloadFile` 装载。 |

近期先做框架内部拆分，共享运行时、首屏导航和业务场景各自维护。继续保留两个开发回归命令，并用 `build:app` 构建可在运行时切换场景的业务样例。后续再为正式构建整理可直接导入微信工具的目录和包内素材。当前工程会排除根目录下的 `assets/`，接入包内素材时要明确复制位置并核对打包清单。

当前 IIFE 中的动态导入用于推迟模块初始化，依赖代码仍留在同一产物。三个体积指标分别核对。源码模块拆分使运行时可复用。输出多个 JS 可以控制单个文件体积，若仍在主包内，全部文件仍计入主包。微信官方分包才会改变主包下载范围。本阶段先完成框架内部拆分。出现工具明确的单文件限制时再拆输出文件，主包体积或首屏耗时成为实际约束时再实施微信官方分包。Draco 是否拆分，由包分析、业务依赖和设备耗时决定。[esbuild 代码拆分](https://esbuild.github.io/api/#splitting) · [微信小游戏分包机制](https://www.tencentcloud.com/zh/document/product/1219/68072)

分别记录构建 JS 字节数、微信工具打包后的主包及各分包体积、从点击到首屏可交互的耗时、运行内存与模型加载时长。资源下载大小、显存占用、主包体积使用各自的测量结果。

## 5. 分阶段实施与验收

此前开发者已验收配装台图集、联合模型、WebGL2 和 `Intl` 修复。业务仍使用 WebGL1。本轮已完成下表第 1 至 3 项的代码及本地验证，微信端按当前业务包重新验收。发布验收等待 HTTPS 下载域名和设备实测。[配装台验收](ARCHITECTURE_AND_USAGE.md#34-框架内部拆分验收)

| 顺序与优先级 | 实施 | 验收标准 |
| --- | --- | --- |
| 1 · P0 整理目录和核心边界 | 先移动模块并更新引用，再把诊断面板从 Pixi 渲染适配移出，把模型描述移到案例场景，最后将配装台的 HUD 和配色数据归到同一场景目录。每步分别运行自动回归。 | 核心无业务和案例引用。配装台的 3D、UI 与状态可在同一目录定位。`build:app` 可离线进入配装台，`build:app:model` 保留真实模型、取消、重试和释放。 |
| 2 · P0 整理启动目标 | 收敛到 `BUILD_PROFILE`，让四类回归案例显式选择场景、HUD 和日志。用现有 npm 命令输出到同一产物路径。 | 严格类型检查和自动回归通过。七种 ES2019 产物都能生成。轻量业务包排除 Draco、独立 UI 和 WebGL2 探针，也排除从 Pixi 适配移出的操作诊断面板。模型诊断和联合构建均保留原模型链路。对比各模式的输出字节数和依赖图。 |
| 3 · P1 新增第二个独立业务场景 | 限时颜色匹配已接入。Three 绘制提示物体，Pixi 提供选择、倒计时、分数与重开。只新增场景文件并连接业务按钮，复用位图数字和现有输入及生命周期接口。 | 微信工具及手机通过计分、相机拖动和按钮互不干扰、返回、重进和前后台验证。首屏与新场景无需资源服务器。[颜色匹配验收](ARCHITECTURE_AND_USAGE.md#38-颜色匹配场景验收) |
| 4 · P1 发布验收 | 核对正式导入目录和资源清单，配置 HTTPS 下载域名。在目标 iOS、Android 关闭开发者调试后扫码。后续可按相同设备矩阵补 WebGL2 支持记录。 | 记录微信包分析、首屏、首次入场时长及设备日志。冷下载成功，热缓存命中，3D、UI、返回和二次进入均通过。按实测结果决定是否拆输出文件或启用微信官方分包。 |

### 5.1 拆分的触发条件

- **当前基线**保留一个 `game.bundle.js`。轻量业务构建排除 GLB／Draco，联合构建保留解码代码，进入模型场景时读取缓存或下载 GLB。业务与 UI 诊断共享独立的包内 PNG，配装台首次进入时解码。把 JS 字节数和微信工具报告的主包大小分别记录，最新数据见[构建基线](ARCHITECTURE_AND_USAGE.md#1-当前基线)。
- **单文件约束**工具明确指出一个 JS 文件超限时，按「启动与共享运行时」「业务」拆出少量 JS，核对依赖图确保 Three 和 Pixi 只有一份，并比较拆分前后的首屏及首次进入场景耗时。
- **主包或下载约束**主包接近实际限额时，先查随包文件、大素材和重复依赖。剔除可独立下载的素材后，如果非首屏代码仍主导体积或启动下载，才启用微信官方普通分包。多个 JS 同属主包时均计入主包。
- **启动或首次入场性能**在相同设备和基础库上分别量从启动到首屏可交互、从点击到场景可交互。冷启动和二次进入分别记录。这样可以判断推迟初始化是否改善体验，或只是把等待转移到首次进入。
