# 微信小游戏框架目标架构与实施路线

路线更新于 2026-11-23。本文定义目标架构和推进顺序。当前可运行的命令、文件与开发指南见[现状与使用指南](ARCHITECTURE_AND_USAGE.md)，已验证事实与历史问题见[QA 文档](QA.md)。

## 1. 基线与目标

保留已经验证的技术组合。应用用 TypeScript 编写，微信小游戏由 `game.js` 加载 ES2019 产物。用 `three-platformize@1.133.3`、WebGL1 与 OrbitControls 渲染 3D，用 `pixi.js@8.23.0` 绘制 UI。初始目标是让不同小游戏复用同一个运行时、场景切换和资源装载方式。

- **渲染**保持一个微信上屏 Canvas、一个 WebGL 上下文和一个帧循环。先 Three 后 Pixi，渲染器交接时重置状态，Pixi 保留 Three 的画面。
- **输入**保留微信原生触摸桥。HUD 根据起点捕获手势并接收释放或取消，其他手势继续交给 OrbitControls。
- **模型**保留适配版 GLTFLoader、静态纯 JS Draco、内嵌贴图、Toon 渐变和动画回归。约 4.13 MB 的 Littlest Tokyo 通过微信下载和版本缓存。
- **兼容性**保留 Pixi 延迟初始化、`navigator`、`globalThis.performance` 映射、WebGL1 的 `LuminanceFormat` 与 DPR 上限 2。
- **验证边界**开发者已确认旧基线的模型和 HUD 操作。本轮以及各阶段的 GPU、设备输入、普通扫码和微信工具分包结果分别验收。Text、图片纹理和滚动组件保持专项验收。

## 2. 模块划分

```text
game.js → 微信构建产物 → src/main.ts
                             │ 选择应用并启动
                             ▼
                       runtime / 微信平台
                      ┌──────┼─────────┐
                  Three 渲染  Pixi HUD   输入路由
                      ▲      ▲         │
                      │      │         │
                      └── 当前场景 ◄───┘
                             │ 请求资源 ID
                             ▼
                 资源清单 → 包内文件 / HTTPS → 版本缓存
                             │
                     GLTFLoader → Draco
```

| 边界 | 职责与所有权 |
| --- | --- |
| `main.ts` | 唯一应用入口。组装运行时、应用配置和首个场景。开发构建可选择已验证的回归样例。 |
| `runtime/` | 拥有 Canvas、平台实例、渲染器、HUD 实例和 RAF。统一窗口、前后台及故障日志。运行时只接收场景行为与 UI 接口，不引用具体关卡。 |
| `platform/` | 保留 `WechatPlatform` 及微信 API 边界。坐标分流、原生触摸与微信生命周期适配在这里或运行时协调。 |
| `scenes/` | 场景拥有自己的 Three Scene、相机、控制器、动画和本场景事件。场景提供进入、逐帧更新、退出与释放能力。管理器只调度活动场景。 |
| `ui/` | Pixi 环境和渲染由运行时挂载。业务页面持有各自的容器和控件状态，通过动作调用场景或业务逻辑。保留已验证的手动手势路由。 |
| `assets/` | 清单记录资源 ID、来源、类型和版本。装载层提供本地文件、远程下载、进度、错误、去重和缓存失效。文件缓存与内存中的已解析对象分开管理。 |
| `draco/`、`rendering/` | 保留现有解码工厂、几何适配与 Toon 材质。场景负责使用，运行时负责绘制。 |

首版只为实际场景建立接口。资源只被一个场景使用时由场景释放。出现确实共享的纹理或模型后，再为共享对象增加引用管理。

## 3. 场景切换与失败恢复

1. 启动创建一次 Canvas、渲染器和 RAF。首页、几何回归场景和模型场景在同一个运行时中切换。断网时首页和基础 HUD 仍可用。
2. 切换过程中保留全局 HUD 与返回操作。旧场景结束前取消手势和异步工作，释放其控制器监听、动画、几何、材质及私有纹理。新场景独立设置相机和渲染配置，避免上一个模型场景的 ACES 等状态泄漏。
3. 模型场景通过资源 ID 获得下载及解析状态。失败要结算为可显示的错误，支持重试或返回。快速往返时，上一尝试的回调只能清理其资源，不能改写当前场景。
4. 处理已复现的 Draco 拒绝与 `GLTFLoader.parse` 等待悬挂。验收覆盖坏 GLB 头、坏 Draco 数据、非 200 和断网。只有内容可用后才将该版本视为有效缓存，现有失败缓存需有失效方案。
5. 切后台时暂停调度并清理手势临时状态。恢复时继续当前场景，首帧不累计后台时间。场景切换生命周期与微信前后台分别建模。

## 4. 构建和资源发布

| 发布层 | 内容与原则 |
| --- | --- |
| 主包 | 微信启动文件、首屏必需的代码、基础 HUD 和小体积本地素材。小图可用单独文件随包发布，并计入包体。 |
| 普通分包 | 后续关卡代码、可选功能和它们专用的小资源。在 `game.json` 声明，使用 `wx.loadSubpackage` 加载。普通分包使用主包共享能力，避免重复构建 Three、Pixi 和平台单例。 |
| HTTPS 静态服务或 CDN | 大模型、高清纹理、音频等内容。按内容版本指定 URL，经合法下载域名和 `wx.downloadFile` 装载。 |

近期先做框架内部拆分，共享运行时、首屏导航和业务场景各自维护。继续保留两个开发回归命令，并用 `build:app` 构建可在运行时切换场景的业务样例。后续再为正式构建整理可直接导入微信工具的目录和包内素材。当前工程会排除根目录下的 `assets/`，接入包内素材时要明确复制位置并核对打包清单。

当前 IIFE 中的动态导入用于推迟模块初始化，依赖代码仍留在同一产物。三个体积指标分别核对。源码模块拆分使运行时可复用。输出多个 JS 可以控制单个文件体积，若仍在主包内，全部文件仍计入主包。微信官方分包才会改变主包下载范围。本阶段先完成框架内部拆分。出现工具明确的单文件限制时再拆输出文件，主包体积或首屏耗时成为实际约束时再实施微信官方分包。Draco 是否拆分，由包分析、业务依赖和设备耗时决定。[esbuild 代码拆分](https://esbuild.github.io/api/#splitting) · [微信小游戏分包机制](https://www.tencentcloud.com/zh/document/product/1219/68072)

分别记录构建 JS 字节数、微信工具打包后的主包及各分包体积、从点击到首屏可交互的耗时、运行内存与模型加载时长。资源下载大小、显存占用、主包体积使用各自的测量结果。

## 5. 分阶段实施与验收

阶段 A 已分离入口和共享运行时，开发者已确认阶段 B、C 及 WebGL2 专项验证通过。WebGL2 的机型、基础库和运行模式细项待补，业务基线保持 WebGL1。阶段 D 的 `Intl` 修复已通过真机验收。配装台已接入同一套 Sprite 和 BitmapText 图集，并通过本地渲染与图片失败回退验证。当前磁盘产物为 `build:app`，新增配装台 UI 待开发者在微信工具和手机复测。[配装台验收](ARCHITECTURE_AND_USAGE.md#34-框架内部拆分验收)

| 阶段 | 实施 | 验收标准 |
| --- | --- | --- |
| B · P0 固定业务基线 | 构建 `build:app`。开发者在微信工具查看主包和最大 JS 文件，在目标手机复测首页、配装台、换色确认、视角、返回重进和前后台。继续用 `build:model` 验证原 GLB／Draco + HUD，按当前构建分别记录。 | 业务模式无资源服务器可启动，重复往返不叠加监听或帧循环，模型模式保留动画和触控。保存实际包分析和预览结果，区分最大单文件、主包总量、冷启动及首次入场耗时。 |
| C · P1 资源恢复与模型场景接入 | 先处理 QA-08 的 Draco 拒绝和外层解析悬挂，覆盖坏 GLB、坏 Draco、非 200 和断网。再通过资源 ID 和版本统一入口，让 Littlest Tokyo 可从同一首页进入和退出，保留独立模型回归命令。 | 失败可见、可重试或返回，失败缓存可失效。退出后异步结果有清理流程，不会附加到新场景。冷下载与热缓存可区分，模型恢复 71 个网格、193,125 个顶点和 `Take 001`，回到首页恢复渲染状态。 |
| W · P1 并行验证 WebGL2 | 用独立诊断入口，先在目标 iOS 和 Android 获取上下文并绘制，再用当前依赖验证 Three／Pixi 同屏。记录两边实际识别的 WebGL 版本。最后跑模型、Toon、遮罩、触控和前后台复测。 | 保持 WebGL1 为当前业务基线。WebGL2 需要在目标设备有完整记录后再进入支持范围。现代 Three.js 升级单独评估，避免把引擎升级和平台适配合到同一轮。 |
| D · P1 业务 UI 和 Agent 工作流 | 建立独立小样验证包内 Sprite，以及 Text 或 BitmapText。给业务场景建立可复用控件、布局和状态示例，保留固定相机、截图位置和手动验收步骤。滚动与列表按业务需求接入。 | 新 UI 按现有场景和输入接口接入，截图和交互在开发者工具及目标手机通过。由后续新场景确认运行时和适配层可直接复用。 |
| E · 发布验收 | 整理正式导入目录和资源清单，配置 HTTPS 下载域名。按本节的体积与性能触发条件决定构建拆分。开发者使用目标 iOS 和 Android 关闭开发者调试后扫码。 | 保留实际主包和文件清单、首屏、首次入场时长及设备日志。冷下载成功，热缓存命中，3D、UI、返回和二次进入均通过。 |

### 5.1 拆分的触发条件

- **当前基线**保留一个 `game.bundle.js`。轻量业务构建排除 GLB／Draco，联合构建保留解码代码，进入模型场景时读取缓存或下载 GLB。业务与 UI 诊断共享独立的包内 PNG，配装台首次进入时解码。把 JS 字节数和微信工具报告的主包大小分别记录，最新数据见[构建基线](ARCHITECTURE_AND_USAGE.md#1-当前基线)。
- **单文件约束**工具明确指出一个 JS 文件超限时，按「启动与共享运行时」「业务」拆出少量 JS，核对依赖图确保 Three 和 Pixi 只有一份，并比较拆分前后的首屏及首次进入场景耗时。
- **主包或下载约束**主包接近实际限额时，先查随包文件、大素材和重复依赖。剔除可独立下载的素材后，如果非首屏代码仍主导体积或启动下载，才启用微信官方普通分包。多个 JS 同属主包时均计入主包。
- **启动或首次入场性能**在相同设备和基础库上分别量从启动到首屏可交互、从点击到场景可交互。冷启动和二次进入分别记录。这样可以判断推迟初始化是否改善体验，或只是把等待转移到首次进入。

### 5.2 分工与待确认项

Agent 负责实现、静态检查、自动回归、依赖图和构建产物。开发者负责微信工具包分析、预览二维码、真机实操和首条错误反馈。P0 从现有产物开始，操作见[业务演示验收步骤](ARCHITECTURE_AND_USAGE.md#34-框架内部拆分验收)。WebGL2 验证前明确目标 iOS／Android 机型和最低基础库。发布验收前确认 HTTPS 资源地址及合法下载域名的配置负责人。
